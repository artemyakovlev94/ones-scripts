# Правила работы с репозиторием

## Структура проекта

- `src/lib/` содержит переиспользуемые вспомогательные скрипты: получение и настройку окружения, работу с файловой системой, чтение конфигурации и другие общие операции. Скрипты в этом каталоге должны решать ограниченную задачу и не должны содержать пользовательские сценарии или полные цепочки бизнес-действий.
- Скрипты из `src/lib/` должны как можно меньше знать о конкретном процессе. Проектируйте их как универсальные библиотеки для работы с отдельной технической областью: файлами, архивами, сетью, окружением и т. п. Передавайте относящиеся к процессу значения через параметры и не зашивайте в библиотеки имена артефактов, переменных окружения или последовательность бизнес-действий.
- `src/workflows/` содержит сценарии, выполняющие цепочки связанных действий. Они могут подключать и использовать скрипты из `src/lib/`, объединяя их в более крупные операции.
- `scripts/` содержит пользовательские точки входа — скрипты, которые пользователь запускает напрямую, например для создания информационной базы 1С. Такие скрипты могут запускать большие цепочки действий и использовать сценарии и вспомогательные скрипты из `src/`.
- `config/.env` содержит переменные, необходимые скриптам. Не размещайте значения переменных окружения непосредственно в коде.
- `docs/` содержит документацию по всем скриптам из `src/lib/`, `src/workflows/` и `scripts/`. Структура документации должна повторять структуру исходников, а `docs/README.md` служит общим индексом.
- `.temp/` предназначена для временных скриптов проверки и тестирования, промежуточных результатов и других временных файлов. Содержимое этого каталога не является частью проекта, может быть удалено в любой момент и не должно использоваться как постоянная зависимость скриптов из `src/` или `scripts/`. Каталог исключён из контроля версий через `.gitignore`; не добавляйте его содержимое в Git принудительно.

## Зависимости между каталогами

- Соблюдайте направление зависимостей: `scripts/` → `src/workflows/` → `src/lib/`.
- `scripts/` также могут напрямую использовать `src/lib/`, если для операции не нужен отдельный workflow.
- Скрипты из `src/lib/` не должны зависеть от `src/workflows/` или `scripts/`.
- Скрипты из `src/workflows/` не должны зависеть от `scripts/`.
- Общую логику, используемую несколькими сценариями, выносите в `src/lib/`; цепочки действий — в `src/workflows/`; непосредственный запуск и обработку пользовательского сценария оставляйте в `scripts/`.

## Инициализация окружения

- В начале каждой пользовательской точки входа подключайте `src/lib/env.os` до остальных скриптов, которым могут понадобиться переменные окружения.
- Сразу после подключения вызывайте экспортную процедуру `Прочитать()` из `src/lib/env.os`, чтобы загрузить значения из `config/.env` и установить переменные окружения до выполнения основной логики.
- Не обращайтесь к переменным окружения до завершения этой инициализации.
- Если новый workflow может запускаться самостоятельно, он также обязан сначала инициализировать окружение. Если workflow вызывается только из уже инициализированной пользовательской точки входа, не дублируйте инициализацию без необходимости.

## Добавление новых скриптов

- Перед добавлением файла определите его роль и поместите его в соответствующий каталог.
- Пользовательские скрипты делайте тонкими: инициализируйте окружение, проверяйте входные данные и передавайте выполнение workflow или вспомогательным модулям.
- Максимально декомпозируйте код на небольшие процедуры и функции с одной ответственностью. Каждый самостоятельный этап, условие или преобразование выносите в отдельную понятную процедуру или функцию, если это упрощает чтение, тестирование или повторное использование. Используйте имена, ясно отражающие назначение, и избегайте длинных методов, в которых смешано несколько уровней логики. Код должен легко читаться сверху вниз и быть удобным для сопровождения.
- Не храните секреты в исходном коде. Каждую новую переменную окружения сразу добавляйте и в рабочий `config/.env`, и в `config/.env.example`, чтобы скрипт был готов к запуску без ручного переноса ключей. В `config/.env` указывайте рабочее значение для текущего окружения, а в `config/.env.example` — безопасный пример без секретов.

## Документация

- Для каждого файла из `src/lib/`, `src/workflows/` и `scripts/` создавайте одноимённый Markdown-файл в соответствующем подкаталоге `docs/`. Например, `src/lib/files.os` документируется в `docs/src/lib/files.md`.
- При добавлении, переименовании, изменении публичного интерфейса или поведения скрипта одновременно обновляйте его страницу документации и ссылки в `docs/README.md`.
- Документация библиотеки должна описывать назначение, публичные процедуры и функции, параметры, возвращаемые значения и важные исключения.
- Документация workflow должна описывать выполняемую цепочку действий, зависимости, входные параметры и результат.
- Документация пользовательского скрипта должна содержать назначение, команду запуска, необходимые переменные окружения и ожидаемый результат.
